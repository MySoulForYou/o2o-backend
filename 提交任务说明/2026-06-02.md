## 🏗️ 1. LBS 附近店铺检索模块设计与实现 (`o2o-shop-service`)

为了给 C 端消费者提供高性能、低延迟的附近商铺检索体验，本项目基于 **Redis GEO 空间索引数据结构** 构建了完整的附近店铺过滤、排序和分页链路：
*   **非持久化距离属性扩展**：在 `Shop.java` 中新增了带有 `@TableField(exist = false)` 注解的 `distance` 字段，专门用于在内存中接收并回传计算得出的物理距离（单位：米），不对底层 MySQL 表结构造成侵入。
*   **附近检索与缓存防击穿装配**：在 `ShopCustomerServiceImpl.java` 中实现了 `pageShopsNearby` 接口。先使用 `opsForGeo().search` 计算出附近指定半径（默认 3km）内的升序排位店铺，经由内存分页截取，再循环调用 `getShopById` 获取店铺详情。该过程完美复用了已有的 **“逻辑过期 + 异步线程重建”** 二级缓存，在防范高并发数据库击穿的同时，回填动态距离。
*   **REST 接口路由匹配**：在 `ShopCustomerController.java` 中暴露了 `GET /shop/customer/shop/nearby` 端点，支持传入经纬度、分类筛选、范围半径与分页参数。

## ⚡ 2. 启动预热与事务绑定双写一致性控制

为确保 Redis 中的 GEO 索引与 MySQL 关系数据库中开店、关店及分类变更的最终状态强一致，模块完成了如下核心机制：
*   **冷启动 GEO 预热加载**：编写了 `ShopGeoPreheatRunner.java`（实现 `CommandLineRunner` 接口），启动时自动将 MySQL 中处于营业状态（`status = 1`）的商铺坐标加载至全局 Key (`o2o:shop:geo:all`) 以及按分类拆分的 Key (`o2o:shop:geo:category:{category}`) 中。
*   **MySQL 事务绑定双写（`Transaction-Bound`）**：重构了 `ShopMerchantServiceImpl.java`。在新增或更新店铺时，通过 `TransactionSynchronizationManager.registerSynchronization` 确保只有当本地事务成功提交（`afterCommit`）后，才执行 `syncRedisGeo` 进行 Redis Geo 同步，避免了事务回滚时导致的缓存脏数据与高并发脏读风险。
*   **精细化同步控制（`syncRedisGeo`）**：对关店/下架状态实施彻底移除；对修改分类（数码 ➡️ 美食）在 Redis 内部执行旧分类 key `remove` 与新分类 key `add` 的安全搬迁，确保 LBS 分页截断逻辑无懈可击。
