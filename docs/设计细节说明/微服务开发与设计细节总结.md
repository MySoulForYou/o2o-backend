# o2o-backend 微服务核心设计与开发细节总结

本文档汇总整理了项目目前**已经实现**的微服务模块、架构设计、技术选型、安全及鉴权机制、以及本地调试细节。

## 🏗️ 一、 已实现的微服务模块与项目架构

目前项目已经搭建完成基础微服务框架，并实现了用户服务（`o2o-user-service`）、网关路由与鉴权（`o2o-gateway`）以及购物车服务（`o2o-cart-service`）的工程骨架：

### 1. 模块结构与端口分配
* **统一网关 (`o2o-gateway`)**：端口 `8080`。负责统一请求入口路由转发，集成全局 JWT 鉴权过滤。
* **用户服务 (`o2o-user-service`)**：端口 `8081`。已实现用户注册/登录、收货地址管理（安全防越权、默认地址单事务更新）。
* **购物车服务 (`o2o-cart-service`)**：端口 `8085`。已完成服务骨架搭建，引入 Nacos 注册中心、MyBatis-Plus、MySQL、Redis、Springdoc Swagger 依赖，配置完毕 Nacos 与多源数据库连接。

### 2. 数据库物理隔离 (MySQL 8.0)
本地 Docker 环境下已创建并初始化以下独立库表：
* `o2o_user_db`：包含用户表 `tb_user`、地址表 `tb_address`。
* `o2o_cart_db`：包含购物车表 `tb_cart`（目前已完成 DDL 建表）。

## 🔒 二、 网关层已实现的路由与全局鉴权

### 1. 路由配置与转发
网关 `o2o-gateway` 的 `application.yml` 中已配置如下路由规则，前缀统一为 `/api`：
* `/api/user/**` -> 转发至 `lb://o2o-user-service`
* `/api/cart/**` -> 转发至 `lb://o2o-cart-service`

### 2. 依赖冲突规避与独立 JWT 验签
* **依赖隔离**：网关服务（基于响应式 WebFlux）未直接引入包含阻塞式 WebMVC 的 `o2o-common` 依赖，避免了类冲突。
* **独立验签**：网关内部独立编写了轻量级的 `JwtUtils`，实现安全的令牌解密与时效校验。

### 3. 全局过滤器 `AuthorizeFilter` (Order: -1)
已实现如下安全过滤与鉴权拦截逻辑：
1. **安全清洗（防伪造 Header）**：所有外部请求（无论是否在白名单内）在进入网关的过滤逻辑前，无条件清除请求头中由客户端携带的 `X-User-Id` 与 `X-User-Name` 头信息，物理隔绝越权欺骗攻击。
2. **白名单判定**：对登录接口 `/**/user/login` 和注册接口 `/**/user/register` 直接放行（经过安全清洗的请求）。
3. **鉴权拦截**：拦截其他非白名单请求，校验 `Authorization` 头中的 JWT Token。若 Token 缺失、失效或过期，直接返回 `401 Unauthorized` 状态码，并以 JSON 格式输出与下游服务结构一致的统一 Result 响应体：`{"code": 401, "message": "未登录或登录已过期", "data": null}`。
4. **身份参数透传**：成功验签后，将从 JWT 中解析出来的真实 `userId` 和 `username` 分别注入请求头 `X-User-Id` 和 `X-User-Name` 中，透传给下游微服务。下游服务已配置全局 `UserContextInterceptor` 拦截器拦截请求，提取并将其暂存入 `UserContext` 的 `ThreadLocal` 容器中。

### 4. 网关全局异常处理器 (`GatewayExceptionHandler`)
* **技术选型**：编写实现 `ErrorWebExceptionHandler` 的组件类并声明高优先级 `@Order(-2)`。
* **作用说明**：拦截网关层产生的网络及路由报错（如：找不到资源 404、微服务宕机/连接拒绝 503 等），将默认的 WebFlux 白页错误包装转化为符合标准 API Result 结构的 JSON 返回体，确保服务故障时响应格式依然统一。

## 🔑 三、 完整登录校验与请求透传流程

对于需要登录态的请求（例如获取收货地址列表 `/api/user/address/list`），系统当前的鉴权与上下文绑定流转逻辑如下：

1. **客户端发起请求**：客户端请求网关入口 `http://localhost:8080/api/user/address/list`，并在请求头中携带 `Authorization: Bearer <Token>`。
2. **网关层拦截与清洗验签**：
   * 网关 `o2o-gateway` 拦截请求，**首先清洗掉客户端可能自带 the 伪造 `X-User-Id` 和 `X-User-Name` 头部**。
   * 解析并校验 JWT Token 的有效性。
   * **若校验失败**（如 Token 缺失或过期），直接将 Response 的 Content-Type 设为 `application/json` 并设置状态码为 `401`，回写统一结果体 `{"code": 401, "message": "未登录或登录已过期", "data": null}` 结束请求。
   * 验签通过后，解析出 Token 中的真实 `userId`，将其作为全新的 `X-User-Id` 请求头塞入并向下游微服务转发。
3. **微服务拦截器绑定线程**：
   * 下游微服务（如 `o2o-user-service`）的 `UserContextInterceptor` 拦截到请求。
   * 在 `preHandle` 阶段，拦截器读取 `X-User-Id` 请求头并将其转换为 Long 类型，执行 `UserContext.setUserId(...)` 将用户 ID 绑定到当前 Tomcat 工作线程的 `ThreadLocal` 变量中。
4. **业务层无参获取**：
   * Controller 层的业务方法不再需要编写 `@RequestHeader` 声明参数，而是直接通过调用静态方法 `UserContext.getUserId()` 从当前线程上下文隐式读取用户 ID。
   * 在数据库操作中强绑定此用户 ID 进行查询，防止越权。
5. **线程上下文清理（防污染）**：
   * 当 HTTP 请求处理完毕并向客户端正常输出响应后，执行拦截器的 `afterCompletion` 回调方法。
   * 方法内执行 `UserContext.clear()` 彻底清空该线程上的 `ThreadLocal` 值，防止 Tomcat 线程池中线程被循环复用时，导致后续无 Token 请求读取到上一次的残留 `userId`。

## 👤 四、 用户与收货地址服务 (已实现逻辑及技术选型)

### 1. 用户账户安全与注册规则控制
* **注册手机号唯一性双重校验**：
  * **技术选型**：在业务逻辑层引入手机号重复查询（`LambdaQueryWrapper`）；在数据库物理约束层为 `tb_user` 表的 `phone` 字段创建唯一索引（`UNIQUE KEY idx_phone (phone)`）。
  * **作用说明**：防止同一手机号多次注册以防范营销刷券套利，并在极高并发下由数据库物理索引排他性兜底。
* **用户名唯一性双重校验**：
  * **技术选型**：业务层校验存在性；数据库层使用 `UNIQUE KEY idx_username (username)` 唯一索引约束。
* **注册入参格式校验（防脏数据）**：
  * **技术选型**：在 `UserServiceImpl.register` 中引入严密的业务层校验（正则与长度限制）：
    * 用户名：必须符合 `^[a-zA-Z0-9_]{4,20}$`（4-20 位字母、数字或下划线）。
    * 密码：长度需控制在 `6-32` 位之间。
    * 手机号：必须匹配中国大陆手机号的标准正则：`^1[3-9]\d{9}$`。
  * **作用说明**：在最前端过滤恶意脏数据，保障数据库数据的合法性与清洁度。
* **安全密码存储 (BCrypt)**：
  * **技术选型**：使用 Spring Security 提供的 `BCrypt` 强哈希加密算法工具。
  * **作用说明**：废弃了传统的 “MD5 + 盐字段” 数据库表列设计，通过密文内嵌随机盐，大幅提升防暴力破解与彩虹表碰撞的安全性，同时简化了表结构。

### 2. 自动透传上下文 (`UserContext`)
* **技术选型**：使用 `ThreadLocal`（封装在自定义工具类 `UserContext` 中）结合 Spring MVC `HandlerInterceptor`（`UserContextInterceptor`）。
* **作用说明**：在微服务入口解析请求头，自动绑定与清除用户身份，免去了 Controller/Service 方法签名中重复声明 `@RequestHeader("X-User-Id")` 的参数污染。

### 3. 收货地址安全逻辑与防刷控制
* **防越权校验**：在 SQL 查询条件中强绑定 `UserContext.getUserId()` 校验，防止垂直越权。
* **单默认地址控制**：使用声明式事务 `@Transactional` 进行排斥性的默认地址字段统一更新。
* **防超限与并发控制**：
  * **技术选型**：采用**“前端层防抖锁定 + 网关层单用户频率限流 + 业务层常规 count() 阈值拦截”**的多重协同防线，拦截手抖及恶意脚本攻击。
  * **代码落地**：在 `AddressServiceImpl.addAddress` 接口开头，声明常量 `MAX_ADDRESS_LIMIT = 20`，每次写入前执行数据库 `count()`，当地址数量大于等于 20 个时直接抛出 `BusinessException` 予以拦截。
  * **决策考量**：对于地址管理这种超低频业务，主动安全地放弃了数据库排他锁和 Redis 分布式锁，以防连接池饿死或带来无谓的架构复杂度（底层技术原理及权衡对比详见 **第六节**）。

## 📖 六、 核心技术原理解析与方案权衡 (技术细节小节)

本节收录了本系统中针对高并发、事务隔离、死锁及微服务环境下的底层技术原理解析，作为设计支撑：

### 1. 数据库事务隔离与“快照读”引发的并发越界问题
* **现象成因**：由于新增地址/注册并非高并发业务，但在手抖或恶意脚本并发请求下（例如限制上限 20 个，当前已存在 19 个，并发 2 个请求），传统的“先 select count() 再 insert 写入”会失效，最终存入 21 条记录，产生并发越界（Race Condition）。
* **底层原理**：
  * MySQL InnoDB 在默认的**可重复读（Repeatable Read, RR）**隔离级别下，采用 **MVCC（多版本并发控制）** 来实现高并发下的读写非阻塞。
  * 执行普通的 `SELECT COUNT(*)` 时属于**快照读（Snapshot Read）**。数据库通过读取 Undo Log 中的数据快照版本返回结果，并不加任何锁。
  * 事务隔离性规定未提交事务的修改对其他事务不可见。当线程 A 还在写入但事务未提交时，并发的线程 B 执行快照读 `count()`，读到的仍然是旧的未超标快照（19 个）。因此两者校验均通过，产生了超限写入。

### 2. 数据库排他锁 (`FOR UPDATE`) 的解决原理与加锁类型
* **排他锁原理**：
  * 将查询写为 `SELECT ... FOR UPDATE` 时，会将快照读升级为**当前读（Current Read）**，并对查询范围加上**排他锁（X-Lock/写锁）**。
  * 当线程 A 占有排他锁时，并发的线程 B 尝试执行相同的查询会被数据库强制阻塞等待（Blocking）。
  * 两个并发请求在数据库层面被迫**串行化（Serialization）**。线程 B 必须等待线程 A 提交事务并释放锁后，才能重新读取到最新的已提交数据（count 为 20），从而校验不通过被拦截。
* **加锁类型深度辨析**：
  * **行级锁（Record Lock）**：当使用**主键或唯一索引**进行**等值查询（`=`）**，且目标记录**在数据库中确实存在**时触发。仅锁定目标数据行本身。
  * **间隙锁（Gap Lock）**：当使用主键或唯一索引进行等值查询，但**记录在数据库中不存在**时触发。MySQL 会锁定数据两旁的开区间，防范其他事务插入。
  * **临键锁（Next-Key Lock）**：InnoDB 的**默认加锁行为**。在进行范围查询，或使用普通非唯一索引查询时触发。它会同时锁定记录本身（行锁）以及记录前后的所有区间（间隙锁）。
  * **全表锁定（类似表锁）**：当 `WHERE` 过滤条件中的字段**没有建立索引**时触发。MySQL 只能通过全表扫描（Full Table Scan）来检索数据，会导致整张表的所有行和全部间隙都被锁死，极大降低系统并发度。

### 3. 间隙锁互等导致的死锁成因分析 (Deadlock)
* **死锁产生环路**：
  间隙锁的一大特性是**间隙锁与间隙锁之间相互兼容**（即并发的多个事务可以同时获得对同一段间隙的锁），但**任何事务都无法向带有间隙锁的区域执行 `INSERT` 操作（插入需要获取插入意向锁，它与间隙锁互斥）**。
  * 事务 A 执行 `FOR UPDATE`，持有了区间 `(10, 20)` 的间隙锁。
  * 事务 B 并发执行 `FOR UPDATE`，由于间隙锁兼容，B 也成功持有了区间 `(10, 20)` 的间隙锁。
  * 事务 A 尝试执行 `INSERT`（被事务 B 的间隙锁阻塞等待）。
  * 事务 B 也尝试执行 `INSERT`（被事务 A 的间隙锁阻断等待）。
  * 双方陷入“互等对方释放间隙锁”的死循环，形成**闭环死锁**，被 MySQL 检测到并强行中断、回滚其中一个事务。

### 4. 为什么低频业务中不推荐排他锁与分布式锁？
* **数据库排他锁的弊端**：会长时间霸占昂贵且有限的数据库 Connection。高并发请求排队时，多余的线程全部会阻塞在 MySQL 处，很容易瞬间打满连接池，导致整个微服务系统的其他无关查询全部因为“连接池饿死”而崩溃；且无索引时有升级为表锁进而产生大面积死锁的风险。
* **分布式锁 (Redis/Redisson) 的弊端**：虽然在内存中完成，不占用数据库连接。但针对收货地址这类低频、偏静态的接口，为此引入锁过期延时（Watchdog）、脑裂防范等配置，属于典型的**过度设计（Over-engineering）**，无端增加了系统运维成本。
* **大厂的黄金性价比组合方案**：“前端按钮防抖置灰（阻断手抖并发） + 网关层速率限制（阻断接口轰炸） + 业务层常规 count() 判定”。既保护了数据库，又实现了代码与系统架构的干净清爽。
