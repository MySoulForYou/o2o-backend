本文档汇总整理了本项目已实现的微服务模块、架构设计、技术选型、安全及鉴权机制，以及商品评价系统的高并发混合存储（Mixed Storage）设计细节，旨在为开发人员提供统一的系统架构与业务流转指南。

## 🏗️ 一、 已实现的微服务模块与项目架构

目前项目已经搭建完成基础微服务框架，并实现了用户服务（`o2o-user-service`）、网关路由与鉴权（`o2o-gateway`）以及购物车服务（`o2o-cart-service`）的工程骨架：

### 1. 模块结构与端口分配
*   **统一网关 (`o2o-gateway`)** [端口: `8080`]：负责统一请求入口路由转发，集成全局 JWT 鉴权过滤。
*   **用户服务 (`o2o-user-service`)** [端口: `8081`]：负责用户注册/登录、收货地址管理（安全防越权、默认地址单事务更新）。
*   **店铺与商品服务 (`o2o-shop-service`)** [端口: `8082`]：负责店铺与商品信息管理、Redis Geo 附近店铺检索，以及高并发单品评价体系。
*   **购物车服务 (`o2o-cart-service`)** [端口: `8085`]：已完成服务骨架搭建，配置完毕 Nacos 与多源数据库连接。

### 2. 数据库物理隔离 (MySQL 8.0)
本地 Docker 环境下已创建并初始化以下独立库表：
*   `o2o_user_db`：包含用户表 `tb_user`、地址表 `tb_address`。
*   `o2o_shop_db`：包含店铺表 `tb_shop`、商品表 `tb_goods`、评价表 `tb_review`（基于单品及订单绑定版）。
*   `o2o_cart_db`：包含购物车表 `tb_cart`。

## 🔒 二、 网关层已实现的路由与全局鉴权

### 1. 路由配置与转发
网关 `o2o-gateway` 的 `application.yml` 中已配置如下路由规则，前缀统一为 `/api`：
*   `/api/user/**` -> 转发至 `lb://o2o-user-service`
*   `/api/shop/**` -> 转发至 `lb://o2o-shop-service`
*   `/api/cart/**` -> 转发至 `lb://o2o-cart-service`

### 2. 依赖冲突规避与独立 JWT 验签
*   **依赖隔离**：网关服务（基于响应式 WebFlux）未直接引入包含阻塞式 WebMVC 的 `o2o-common` 依赖，避免了 Netty 与 Tomcat 的类冲突。
*   **独立验签**：网关内部独立编写了轻量级的 `JwtUtils`，实现安全的令牌解密与时效校验。

### 3. 全局过滤器 `AuthorizeFilter` (Order: -1)
已实现如下安全过滤与鉴权拦截逻辑：
1.  **安全清洗（防伪造 Header）**：所有外部请求（无论是否在白名单内）在进入网关的过滤逻辑前，无条件清除请求头中由客户端携带的 `X-User-Id` 与 `X-User-Name` 头信息，物理隔绝越权欺骗攻击。
2.  **白名单判定**：对登录接口 `/**/user/login` 和注册接口 `/**/user/register` 直接放行（经过安全清洗的请求）。
3.  **鉴权拦截**：拦截其他非白名单请求，校验 `Authorization` 头中的 JWT Token。若 Token 缺失、失效或过期，直接返回 `401 Unauthorized` 状态码，并以 JSON 格式输出与下游服务结构一致的统一 Result 响应体。
4.  **身份参数透传**：成功验签后，将从 JWT 中解析出来的真实 `userId` 和 `username` 分别注入请求头 `X-User-Id` 和 `X-User-Name` 中，透传给下游微服务。下游服务已配置全局 `UserContextInterceptor` 拦截器拦截请求，提取并将其暂存入 `UserContext` 的 `ThreadLocal` 容器中。

### 4. 网关全局异常处理器 (`GatewayExceptionHandler`)
*   **技术选型**：编写实现 `ErrorWebExceptionHandler` 的组件类并声明高优先级 `@Order(-2)`。
*   **作用说明**：拦截网关层产生的网络及路由报错（如：找不到资源 404、微服务宕机/连接拒绝 503 等），将默认的 WebFlux 白页错误包装转化为符合标准 API Result 结构的 JSON 返回体，确保服务故障时响应格式依然统一。

## 🔑 三、 完整登录校验与请求透传流程

对于需要登录态的请求，系统当前的鉴权与上下文绑定流转逻辑如下：

1.  **客户端发起请求**：客户端请求网关入口 `http://localhost:8080/api/user/address/list`，并在请求头中携带 `Authorization: Bearer <Token>`。
2.  **网关层拦截与清洗验签**：
    *   网关 `o2o-gateway` 拦截请求，首先清洗掉客户端可能自带的伪造 `X-User-Id` 和 `X-User-Name` 头部。
    *   解析并校验 JWT Token 的有效性。若校验失败，直接将 Response 的 Content-Type 设为 `application/json` 并设置状态码为 `401`，回写统一结果体结束请求。
    *   验签通过后，解析出 Token 中的真实 `userId`，将其作为全新的 `X-User-Id` 请求头塞入并向下游微服务转发。
3.  **微服务拦截器绑定线程**：
    *   下游微服务（如 `o2o-user-service`）的 `UserContextInterceptor` 拦截到请求。
    *   在 `preHandle` 阶段，拦截器读取 `X-User-Id` 请求头并将其转换为 Long 类型，执行 `UserContext.setUserId(...)` 将用户 ID 绑定到当前 Tomcat 工作线程的 `ThreadLocal` 变量中。
4.  **业务层无参获取**：
    *   Controller 层的业务方法不再需要编写 `@RequestHeader` 声明参数，而是直接通过调用静态方法 `UserContext.getUserId()` 从当前线程上下文隐式读取用户 ID。在数据库操作中强绑定此用户 ID 进行查询，防止垂直越权。
5.  **线程上下文清理（防污染）**：
    *   当 HTTP 请求处理完毕并向客户端正常输出响应后，执行拦截器的 `afterCompletion` 回调方法。
    *   方法内执行 `UserContext.clear()` 彻底清空该线程上的 `ThreadLocal` 值，防止 Tomcat 线程池中线程被循环复用时，导致后续无 Token 请求读取到上一次的残留 `userId`。

## 👤 四、 用户与收货地址服务设计

### 1. 用户账户安全与注册规则控制
*   **注册手机号唯一性双重校验**：在业务逻辑层引入手机号重复查询（`LambdaQueryWrapper`）；在数据库物理约束层为 `tb_user` 表的 `phone` 字段创建唯一索引（`UNIQUE KEY idx_phone`）。
*   **安全密码存储 (BCrypt)**：使用 Spring Security 提供的 `BCrypt` 强哈希加密算法工具，通过密文内嵌随机盐，大幅提升防暴力破解与彩虹表碰撞的安全性，同时简化了表结构。
*   **注册入参格式校验（防脏数据）**：
    *   用户名：必须符合 `^[a-zA-Z0-9_]{4,20}$`（4-20 位字母、数字或下划线）。
    *   密码：长度需控制在 `6-32` 位之间。
    *   手机号：必须匹配中国大陆手机号的标准正则：`^1[3-9]\d{9}$`。

### 2. 收货地址安全逻辑与防刷控制
*   **防越权校验**：在 SQL 查询条件中强绑定 `UserContext.getUserId()` 校验，防止垂直越权。
*   **单默认地址控制**：使用声明式事务 `@Transactional` 进行排斥性的默认地址字段统一更新。
*   **防超限与并发控制**：
    *   **方案选择**：在 `AddressServiceImpl.addAddress` 接口开头，声明常量 `MAX_ADDRESS_LIMIT = 20`，每次写入前执行数据库 `count()`，当地址数量大于等于 20 个时直接抛出 `BusinessException` 予以拦截。
    *   对于地址管理这种超低频业务，主动放弃了数据库排他锁和 Redis 分布式锁，以防连接池饿死或带来无谓的架构复杂度，采用“前端按钮防抖置灰 + 网关层速率限制 + 业务层常规 count() 判定”的黄金性价比组合方案。

## 🏪 五、 店铺评价系统：混合存储与高并发架构设计

在商品评价系统设计中，单表 MySQL 方案在数据量达到百万级以上时，会因**行溢出引发随机 I/O 暴涨**、**B+ 树分裂导致缓存失效**以及**模糊搜索（LIKE '%xxx%'）引发全表扫描**而崩溃。为此，系统采用了大厂主流的混合存储架构与高并发防击穿方案。

### 1. 混合存储分工体系（Mixed Storage）

为了将“关系强绑定”、“海量文本存储”、“多维检索”与“高频统计”彻底拆分，各组件职责划分如下：

*   **MySQL（事务级元数据）**：仅存储评价ID、订单ID、商品ID、店铺ID、用户ID、星级评分、状态标识等定长轻量字段。**保持单行记录约 50 字节**，单页容纳 300+ 行，保证索引树小且常驻内存，**防刷单联合唯一索引校验极快**。
*   **MongoDB（非结构化长文本与晒图库）**：专门以 BSON 文档形式存储用户的长篇文字评论、商家回复、图片/视频 URL 数组。实现**单次读写（Single Read/Write）**，彻底避免 MySQL 行溢出与表关联。*（注：当前开发处于第一阶段 MVP，为简化开发与测试，我们采用渐进式方案，长文本与晒图链接先在 MySQL 中建表存储，待后期架构演进时再彻底迁入 MongoDB。）*
*   **Elasticsearch（高性能检索服务）**：同步扁平化汇总的评价索引（包含分词文本、有图/星级/追评等过滤标识位）。**前台所有的评价列表页与多维筛选均 100% 走 ES 检索**，完全不触碰 MySQL，隔离读写压力。
*   **Redis（高频统计与数据缓存）**：存储店铺/商品的统计计数器（好评率、总评论数等）以便秒级读取，抗住高并发检索压力。

### 2. 核心业务流程流转逻辑

#### ① 发布评价流程（写链路）
用户提交评价（携带 `orderId`, `goodsId`, `score`, `content`） ➔ 网关校验 Token 并透传 `userId` ➔ **店铺服务（shop-service）接收请求，通过 Feign 远程调用交易服务（trade-service）校验订单真实性（用户是否确实购买过该商品且订单已完成）** ➔ 校验通过，核心元数据写入 MySQL，长文本与媒体字段写入 MongoDB ➔ 成功返回并向 RabbitMQ 发送消息 `review.published` ➔ 各服务异步消费：交易服务更新订单评价状态、店铺服务异步同步数据至 ES 并更新 Redis 统计计数器、用户服务发放积分。

#### ② 检索评价流程（读链路）
用户在详情页翻阅商品评价时 ➔ 店铺服务接收请求，将过滤参数（有图、好评、关键词等）拼接为 DSL，查询 **Elasticsearch** ➔ ES 返回匹配的评价 ID 列表（分页） ➔ 店铺服务根据 ID 列表，从 **MongoDB** 批量拉取富文本内容 ➔ 提取 `userId` 列表，通过 Feign 批量拉取用户服务的最新昵称与头像进行内存装配，最终返回前端展示。

## 📖 六、 核心技术原理解析与方案权衡

### 1. 数据库事务隔离与“快照读”引发的并发越界问题
由于新增地址/注册并非高并发业务，但在手抖或恶意脚本并发请求下，传统的“先 select count() 再 insert 写入”会失效，产生并发越界（Race Condition）。
*   **底层原理**：MySQL InnoDB 在默认的可重复读（Repeatable Read, RR）隔离级别下，采用 MVCC（多版本并发控制）来实现高并发下的读写非阻塞。执行普通的 `SELECT COUNT(*)` 时属于快照读（Snapshot Read），读取的是 Undo Log 中的数据快照版本，并不加任何锁。
*   当事务 A 还在写入但未提交时，并发的事务 B 执行快照读，读到的仍然是旧的未超标快照，因此校验均通过，最终导致超限写入。

### 2. 数据库排他锁 (`FOR UPDATE`) 的解决原理与加锁类型
*   **排他锁原理**：将查询写为 `SELECT ... FOR UPDATE` 时，会将快照读升级为当前读（Current Read），并对查询范围加上排他锁（X-Lock/写锁）。并发的事务 B 尝试执行相同的查询会被强制阻塞等待。两个并发请求在数据库层面被迫串行化。
*   **加锁类型**：
    *   **行级锁（Record Lock）**：当使用主键或唯一索引进行等值查询，且目标记录存在时触发。仅锁定目标数据行。
    *   **间隙锁（Gap Lock）**：当使用主键或唯一索引进行等值查询，但记录不存在时触发。MySQL 会锁定数据两旁的开区间，防范其他事务插入。
    *   **临键锁（Next-Key Lock）**：InnoDB 的默认加锁行为。在进行范围查询，或使用普通非唯一索引查询时触发。它会同时锁定记录本身（行锁）以及记录前后的所有区间（间隙锁）。
    *   **全表锁定**：当 `WHERE` 过滤条件中的字段没有建立索引时触发。MySQL 只能通过全表扫描来检索数据，会导致整张表的所有行和全部间隙都被锁死，极大降低系统并发度。

### 3. 间隙锁互等导致的死锁成因分析 (Deadlock)
*   **死锁产生环路**：间隙锁与间隙锁之间相互兼容（即并发的多个事务可以同时获得对同一段间隙的锁），但任何事务都无法向带有间隙锁的区域执行 `INSERT` 操作（插入需要获取插入意向锁，它与间隙锁互斥）。
*   事务 A 执行 `FOR UPDATE`，持有了区间 `(10, 20)` 的间隙锁。事务 B 并发执行 `FOR UPDATE`，也持有了该间隙锁。随后事务 A 尝试 `INSERT` 被事务 B 阻塞；事务 B 尝试 `INSERT` 被事务 A 阻塞。双方陷入“互等对方释放间隙锁”的死循环，形成闭环死锁。
