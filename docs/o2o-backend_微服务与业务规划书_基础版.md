# o2o-backend：基于微服务架构的智能 O2O 聚合电商平台 (基础版)

> **💡 项目说明**：
> 本项目是以 **高性能微服务 O2O 商城** 为业务主体的企业级工程。项目名称 `o2o-backend` 对应后台核心代码仓库。
> 本版本为 **纯后端基础版**，剔除了大模型与 AI 相关的高延迟业务，专注于微服务基础架构、高并发秒杀削峰、Redis 缓存设计、地理位置（LBS）检索以及经典的分布式一致性业务，确保逻辑 100% 贴合企业级实际研发规范，是打牢后端底子的最佳实践。

## 🎯 一、 简历项目介绍（可直接用于简历）

*   **项目名称**：`o2o-backend`（基于微服务架构的智能 O2O 聚合电商平台）
*   **技术选型**：Spring Boot, Spring Cloud Gateway, Nacos, Sentinel, Redis, Redisson, RabbitMQ, MySQL 8.0, MyBatis-Plus, Docker.
*   **项目背景**：本平台为 O2O（Online to Offline）聚合电商系统，提供同城商铺检索、购物车管理、高并发抢购（秒杀）等核心业务。针对同城高并发搜索、商铺详情高频访问导致的数据库压力、以及活动期间瞬时流量洪峰等生产痛点，设计并研发了这套高性能、高可用的微服务电商后台。
*   **个人职责与业务成效（STAR 格式）**：
    1.  **【网关统一鉴权与流控】**：基于 **Spring Cloud Gateway** 搭建系统入口，统一实现基于 JWT 的用户登录态校验，并通过 **Redis 限流令牌桶** 算法对各业务接口进行流量限制，拦截恶意刷量请求，保障网关层高可用。
    2.  **【高并发店铺评价缓存设计】**：针对商铺详情页中“店铺评价汇总”高频访问、易导致数据库击穿的痛点，采用 **Redis 逻辑过期策略与 Redisson 分布式锁**。在高并发缓存失效时，平滑返回旧数据，仅由唯一抢锁成功的线程去异步重构缓存，服务可用性达 **99.99%**。
    3.  **【附近商铺 LBS 地理检索】**：利用 **Redis Geo** 结构存储并检索同城商铺位置数据。支持用户根据当前经纬度检索 3 公里范围内的附近店铺，并按距离进行升序排列，检索平均响应时间控制在 **20ms** 以内。
    4.  **【秒杀高并发削峰与安全防刷】**：针对秒杀活动中的超高吞吐量与瞬时洪峰，设计了 **Redis Lua 库存预扣 + RabbitMQ 异步排队** 的组合架构。实现内存级别的库存扣减并立即返回“排队中”，异步消费者平滑落库建单，实现对数据库的物理削峰，确保系统在万级 QPS 下稳定运行。
    5.  **【微服务解耦与 RPC 调用规范】**：采用接口与实现物理隔离的 Maven 多模块设计。在 `o2o-api` 模块中声明 FeignClient，避免了微服务之间的循环依赖；实现 Feign 请求拦截器自动透传网关解析的 JWT 身份 Header，保障跨服务调用的安全与一致性。

## 🏗️ 二、 多模块项目架构图与职责划分

系统采用标准的 Maven 多模块（Multi-Module）物理隔离设计，整体依赖与服务关系如下：

### 1. 架构关系图

```
o2o-backend (父工程：负责锁定全项目依赖版本，不写业务代码)
 ├── o2o-common (公共底座：统一返回类、全局异常拦截、通用常量枚举、JWT解析工具类)
 ├── o2o-api    (远程调用：微服务间 RPC 的 FeignClient 接口定义、跨服务传输 DTO 对象)
 ├── o2o-gateway [8080] (独立运行微服务：负责路由转发、JWT验签、网关全局限流)
 ├── o2o-user-service [8081] (独立运行微服务：负责用户登录/注册、收货地址管理、Redis购物车)
 ├── o2o-shop-service [8082] (独立运行微服务：负责店铺与商品管理、Redis Geo 附近店铺检索、店铺评价缓存)
 └── o2o-trade-service [8083] (独立运行微服务：负责普通订单、秒杀预扣库存、MQ异步建单削峰)
```

### 2. 各子模块职责详细分工

*   **`o2o-common` (公共基础包 - 被所有子服务依赖)**：
    *   **统一返回结果类 (`Result<T>`)**：规范前端 API 数据交互格式。
    *   **全局异常拦截器 (`GlobalExceptionHandler`)**：统一捕获运行期异常，对外返回友好错误，防止系统堆栈外泄。
    *   **通用工具与配置**：包含密码加密工具、日期处理工具及 Redis 配置模板。
*   **`o2o-api` (远程调用声明包 - 被调用端依赖)**：
    *   **FeignClient 声明接口**：如 `UserClient`、`ShopClient`。下游服务通过注入接口即可发起 RPC 调用，物理上隔绝了子服务之间直接引用包结构导致的微服务循环依赖。
    *   **跨服务数据传输对象 (`DTO`)**：定义微服务间数据传输的标准格式（如 `UserDto`、`OrderDto`）。
*   **`o2o-gateway` (统一网关服务 — 端口 8080)**：
    *   路由转发，隐藏后端微服务真实端口。
    *   JWT 登录令牌验签，并提取 `userId` 写入请求头（Header）透传给下游。
    *   集成 Redis 限流过滤器，防止接口被刷。
*   **`o2o-user-service` (用户服务 — 端口 8081)**：
    *   用户注册与密码/验证码登录逻辑。
    *   用户收货地址簿管理（包含地址的 LBS 经纬度坐标数据）。
    *   基于 **Redis Hash** 结构的高并发购物车暂存与管理。
*   **`o2o-shop-service` (商铺与搜索服务 — 端口 8082)**：
    *   商品基本分类与店铺数据维护。
    *   基于 **Redis Geo** 进行 3 公里内的附近店铺地理位置检索。
    *   基于 **Redisson 分布式锁与逻辑过期策略** 实现店铺评价缓存的高并发安全展示（防止缓存击穿）。
*   **`o2o-trade-service` (交易与秒杀服务 — 端口 8083)**：
    *   普通订单创建、扣减物理库存、结算购物车，开启本地事务保证一致性。
    *   秒杀高并发 Redis Lua 库存预扣减，并投递到 RabbitMQ 队列进行异步建单。

## 💬 三、 4 大核心业务场景流转流程

### 1. 附近商铺 LBS 地理检索与详情页展示
*   **业务场景描述**：
    用户打开 App 首页，展示距离自己 3 公里内的店铺列表；点击店铺进入详情页，查看店铺基本信息与评价汇总。
*   **业务流转**：
    1.  **LBS 检索**：前端上传用户当前经纬度，`o2o-shop-service` 接收请求，利用 `Redis GEORADIUS` 检索 3 公里内所有店铺。
    2.  **排序与回表**：Redis 返回店铺 ID 以及距离数值，服务对 ID 进行分页并关联 MySQL 获取店铺的基础信息（店铺名、图片等），按距离升序返回。
    3.  **详情展示与评价缓存**：用户点击店铺进入详情页，系统查询店铺评价汇总。此时优先查 Redis：
        *   若 Redis **未过期**，直接返回。
        *   若 Redis **已逻辑过期**，主线程不阻塞，直接返回旧缓存（保活）。同时异步开启一个线程尝试获取 `Redisson` 分布式锁，获取成功的线程从 MySQL 重新统计评价数据、写回 Redis 重设过期时间并释放锁；其余没抢到锁的并发请求快速返回旧数据。

### 2. 用户登录态校验与微服务信息透传
*   **业务场景描述**：
    用户在购物车或结算时，系统如何判断用户已登录，并获取当前用户 ID。
*   **业务流转**：
    1.  **网关校验**：用户请求携带 `Authorization` (JWT token) 到达 `o2o-gateway`。
    2.  **解析与透传**：网关拦截器校验 JWT 合法性，解析出 `userId`，并在路由转发时，在 Request 中新增一个自定义 Header `X-User-Id`。
    3.  **微服务拦截**：下游业务微服务（如 `user-service` 购物车接口）的 `WebMvcInterceptor` 拦截器拦截请求，读取 Header `X-User-Id`，并存入当前线程的 `ThreadLocal`（如 `UserContextHolder`）。
    4.  **业务获取**：业务层（Controller / Service）直接从 `UserContextHolder` 获取 `userId` 开展购物车操作。

### 3. 高并发秒杀削峰与异步建单
*   **业务场景描述**：
    秒杀活动开始，用户点击“抢购”1元优惠券。
*   **业务流转**：
    1.  **库存预热**：秒杀活动开始前，管理员将商品秒杀库存同步到 Redis 中。
    2.  **库存预扣 (Redis Lua)**：用户发起抢购，请求到达 `o2o-trade-service`。使用 **Redis Lua 脚本** 进行判断：若库存充足则扣减 Redis 库存并返回成功；若不足则立即返回“已售罄”。（Lua 保证了“判断+扣减”的原子性，防止超卖）。
    3.  **投递消息 (RabbitMQ)**：Redis 扣减成功后，服务向 RabbitMQ 发送一条包含“用户ID”和“秒杀商品ID”的下单消息，并立即向前端返回“排队中，请稍候”。
    4.  **异步消费与落库**：秒杀下单消费者从 RabbitMQ 消费消息，扣减 MySQL 中的真实物理库存，并在数据库中生成订单，修改订单状态为“待支付”。
    5.  **前端轮询**：前端收到“排队中”后，每隔 1-2 秒轮询一次订单状态接口，当查询到订单生成成功后跳转到支付页面。

### 4. 跨服务购物车结算与 RPC 调用
*   **业务场景描述**：
    用户在购物车勾选商品点击“去结算”，生成普通订单并清空购物车。
*   **业务流转**：
    1.  **下单请求**：用户请求发送给 `o2o-trade-service` 创建订单。
    2.  **信息校验 (Feign 调用)**：
        *   `trade-service` 通过 Feign 远程调用 `user-service` 获取用户购物车中勾选的商品列表及总价。
        *   通过 Feign 远程调用 `shop-service` 校验当前商品库存是否充足、商品是否下架。
    3.  **分布式 Header 传递**：在 Feign 调用期间，通过 Feign 请求拦截器 `RequestInterceptor` 将当前线程 `ThreadLocal` 里的 `X-User-Id` 自动复制到 Feign 的 Outgoing Headers 中，确保下游微服务通过 RPC 也能感知当前操作的用户。
    4.  **事务落库与清理**：`trade-service` 扣减本地库存表、写入订单表，在一个本地声明式事务 (`@Transactional`) 中保证一致性。落库成功后，异步通知 `user-service` 清空已购买的购物车商品。
