# o2o-backend：基于微服务架构的大模型网关与智能 O2O 聚合电商平台

> **💡 项目说明**：
> 本项目是以 **高性能微服务 O2O 商城** 为业务主体，并融入 **大模型算力控制网关与 Agent 智能助理** 的企业级工程。项目名称 `o2o-backend` 对应后台核心代码仓库。
> 
> 本规划书采用 **“1个父工程 + 2个公共依赖包 + 5个运行微服务”** 的多模块（Multi-Module）架构设计，专注于在纯线上场景下将系统业务流转与架构职责讲清楚，确保逻辑 100% 贴合企业级实际研发规范。

---

## 🎯 一、 简历项目介绍（直接复制至简历中）

*   **项目名称**：`o2o-backend`（基于微服务架构的大模型网关与智能 O2O 聚合电商平台）
*   **技术选型**：Spring Cloud Gateway (WebFlux / Netty), Nacos, Sentinel, Redis, Redisson, RabbitMQ, LangChain4j, Milvus (向量数据库), MySQL 8.0, Docker.
*   **项目背景**：平台在引入 AI 功能（智能导购 Agent、商铺评价 AI 总结、秒杀 AI 风控、大模型语义搜索）后，由于大模型接口高延迟、高计费和极不稳定等特性，面临着接口费用失控、高并发缓存击穿、第三方大模型服务故障宕机以及智能黄牛脚本刷单等真实的生产痛点。为此研发了这套集成了 AI 算力管控的高并发 O2O 聚合商城后台。
*   **个人职责与业务成效（STAR 格式）**：
    1.  **【AI 算力额度管控业务】**：针对各部门接入大模型成本失控的痛点，在网关层设计了统一的算力管控模块，利用 **Redis + Lua 脚本** 实现了基于 Prompt 字符长度预测的 Token 限流业务，对各业务线进行秒级算力额度控制，拦截异常刷量，**Token 费用降低约 35%**。
    2.  **【高可用降级切换业务】**：集成 Sentinel 监控外部模型（如 DeepSeek）响应指标。当主模型接口发生超时或故障时，网关在 100ms 内平滑降级切换至备用模型（如通义千问），保障大模型业务 **99.99% 的高可用性**。
    3.  **【高延迟 AI 缓存保障业务】**：针对“商铺 AI 评价摘要”计算慢、易被并发请求击穿的业务痛点，采用 **Redisson 分布式锁与逻辑过期策略**。高并发下缓存过期时不阻塞用户，直接返回旧摘要（兜底），仅由唯一抢锁成功的线程去异步调用模型重构缓存，服务可用性达 **99.999%**。
    4.  **【秒杀削峰与 AI 风控业务】**：针对 1 元券抢购活动中的智能黄牛脚本，设计了 **Redis Lua 库存预扣 + RabbitMQ 异步排队 + 大模型风控拦截** 的组合拳业务。在落库前异步调用风控大模型进行黄牛意图识别，阻断恶意抢单，**黄牛拦截率达 98%**。
    5.  **【大模型向量语义检索与 Agent 闭环】**：基于 LangChain4j 与向量数据库（Milvus/Redis Vector）设计了智能搜索与导购 Agent 业务。提取商铺 AI 摘要转化为向量进行存储，用户使用大白话搜索时通过向量相似度精准推荐商铺；同时利用 **Function Calling（工具调用）** 解析用户指令代其调用底层商城接口（如加购），实现“自然语言对话即交易”的业务闭环。

## 🏗️ 二、 多模块项目架构图与职责划分

系统采用大厂标准的 Maven 多模块物理隔离设计，整体依赖与服务关系如下：

### 1. 架构关系图

```
o2o-backend (父工程：负责锁定全项目依赖版本，不写业务代码)
 ├── o2o-common (公共底座：统一返回类、全局异常拦截、通用常量枚举、JWT解析工具类)
 ├── o2o-api    (远程调用：微服务间 RPC 的 FeignClient 接口定义、跨服务传输 DTO 对象)
 ├── o2o-gateway [8080] (独立运行微服务：负责鉴权、算力 Token 限流、外部模型故障熔断)
 ├── o2o-user-service [8081] (独立运行微服务：负责用户资料、收货地址、Redis购物车管理)
 ├── o2o-shop-service [8082] (独立运行微服务：负责店铺与商品信息、Redis GeoLBS检索、评价AI摘要、Qdrant语义搜索)
 ├── o2o-trade-service [8083] (独立运行微服务：负责普通订单、秒杀预扣库存、MQ异步排队、AI黄牛风控拦截)
 └── o2o-agent-service [8084] (独立运行微服务：负责AI对话历史管理、Function Calling工具函数绑定与微服务RPC代理)
```

### 2. 各子模块职责详细分工

*   **`o2o-common` (公共基础包 - 被所有子服务依赖)**：
    *   **统一返回结果类 (`Result<T>`)**：规范前端 API 数据交互格式。
    *   **全局异常拦截器 (`GlobalExceptionHandler`)**：拦截底层异常，对外返回友好错误，防止系统堆栈外泄。
    *   **通用工具与配置**：包含密码加密工具、日期处理工具及 Redis 配置模板。
*   **`o2o-api` (远程调用声明包 - 被调用端依赖)**：
    *   **FeignClient 声明接口**：如 `UserClient`、`ShopClient`。下游服务通过 autowire 注入接口即可发起 RPC 调用，从物理上隔绝了子服务之间直接引用包结构导致的**微服务循环依赖**。
    *   **跨服务数据传输对象 (`DTO`)**：定义微服务间数据传输的标准格式（如 `UserDto`、`OrderDto`）。
*   **`o2o-gateway` (统一网关服务 — 物理独立运行，端口 8080)**：
    *   JWT 登录令牌验签与权限拦截。
    *   大模型 Token 算力额度预测限流与内容合规过滤。
    *   集成 Sentinel 对第三方 API（如 DeepSeek）进行熔断，异常时秒级平滑降级切换至备用模型（如通义千问）。
*   **`o2o-user-service` (用户服务 — 物理独立运行，端口 8081)**：
    *   用户注册与密码/验证码登录逻辑。
    *   用户收货地址簿管理（提供 LBS 坐标点数据）。
    *   基于 **Redis Hash** 的高并发购物车暂存管理。
*   **`o2o-shop-service` (商铺与搜索服务 — 物理独立运行，端口 8082)**：
    *   基于 **Redis Geo** 进行 3 公里内的附近店铺地理位置检索。
    *   基于 **Redisson 分布式锁与逻辑过期策略** 实现店铺评价 AI 总结的高并发展示（保护高延迟大模型调用不击穿缓存）。
    *   基于向量数据库实现的**大模型语义搜索**。
*   **`o2o-trade-service` (交易与秒杀服务 — 物理独立运行，端口 8083)**：
    *   普通订单创建、扣减物理库存、结算购物车，开启本地事务保证一致性。
    *   秒杀高并发 Redis Lua 库存预扣减，并投递到 RabbitMQ 队列进行异步建单。
    *   在写库建单前，异步调用风控模型，识别刷单黄牛账号并执行库存回滚与阻断。
*   **`o2o-agent-service` (智能助理服务 — 物理独立运行，端口 8084)**：
    *   在 Redis 中维护用户的多轮对话上下文会话。
    *   利用大模型的 **Function Calling** 机制将大白话需求转化为微服务接口调用参数，自动触发下游 Feign 接口进行商品检索及加购，打通“对话即加购”的智能交易闭环。

## 💬 三、 5 大核心业务场景流转流程

### 1. 智能导购与自助交易闭环业务
*   **业务场景描述**：
    用户在聊天框输入一句话：“帮我找个附近便宜的充电宝，直接加到我的购物车里。” 整个后台流转如下：
*   **业务流转**：
    1.  **意图翻译**：`o2o-agent-service` 接收到提问，调用大模型将其翻译为系统指令：`searchNearbyShops(keyword="充电宝", radius=1000, sort="price_asc")`。
    2.  **获取商品**：Agent 代用户触发 Feign 接口（FeignClient 定义在 `o2o-api` 中），调用 `o2o-shop-service` 的检索服务，获取符合位置和价格的商品。
    3.  **自动加购**：Agent 拿到数据后，自动触发 `o2o-user-service` 的购物车添加接口，将该商品直接塞进用户的购物车中。
    4.  **打字机流式响应**：AI 导购管家在聊天框中向用户进行打字机流式（SSE）消息反馈：“已为您放进购物车，可以直接去结算了！”

### 2. 大模型向量语义搜索业务 (RAG)
*   **业务目标**：解决传统 SQL 模糊搜索无法理解用户真实意图的痛点，实现语义层面的商铺精准匹配。
*   **业务流转**：
    1.  系统后台提取商铺的 AI 评价摘要，利用 Embedding 模型将其转化为向量，写入向量数据库。
    2.  用户在前台搜索框输入语义化文本（如：“适合情侣约会的安静西餐厅”）。
    3.  `o2o-shop-service` 将用户的搜索词转化为向量，去向量数据库中进行余弦相似度匹配。
    4.  向量库返回匹配度最高的商铺 ID 列表，服务结合 MySQL 基础商铺信息和 LBS 距离数据进行综合排序，毫秒级呈献给用户。

### 3. AI 店铺评价自动汇总业务
*   **业务目标**：省去用户翻阅数百条评价的时间，在详情页直接展示极简的 AI 评价摘要，并用锁机制防范大模型高并发调用成本。
*   **业务流转**：
    1.  商铺新产生的评论存入 MySQL。用户请求商铺详情时，系统优先查 Redis 缓存。
    2.  若 Redis 中的缓存过期（逻辑过期时间已到），线程不阻塞，直接向前端返回旧摘要（保活）。
    3.  该线程尝试获取 Redisson 分布式锁。抢锁成功的 1 个线程在后台开启异步任务，去调用 AI 接口总结评价并写回 Redis 重设过期时间；其余没抢到锁的并发线程同样快速返回旧数据。

### 4. 高并发秒杀与 AI 风控黄牛拦截业务
*   **业务目标**：保障秒杀超高吞吐量的同时，防范智能脚本刷单，保护真实消费者的利益。
*   **业务流转**：
    1.  秒杀开启，用户请求到达 `o2o-trade-service`，直接在 Redis 中执行 Lua 脚本原子性预扣库存，成功后发送凭证进入 RabbitMQ 队列，并立即返回给用户“排队中”。
    2.  下单消费者从 RabbitMQ 消费消息，拉取用户的设备指纹、下单间隔等行为数据，异步发送给网关的风控大模型。
    3.  风控大模型返回黄牛风险分值。若判定为黄牛，直接作废凭证并回滚 Redis 虚拟库存；若判定为真实用户，才真正写库出单并通知用户付款。

### 5. 大模型算力限流与安全防护业务
*   **业务目标**：在网关层对不同业务线（如客服、导购）进行安全审计，并防止大模型 Token 成本超支。
*   **业务流转**：
    1.  用户发起的 AI 请求经过 `o2o-gateway`。
    2.  网关执行敏感词及越狱注入词过滤，保护提示词安全。
    3.  网关根据 Prompt 字符数预测本次请求将耗费的 Token 量。
    4.  网关调用 Redis Lua 脚本扣减该业务线 AppKey 对应的限流令牌桶。若 Token 余额不足，直接拦截并返回 `429` 状态码，避免算力池被高频异常流量耗尽。
